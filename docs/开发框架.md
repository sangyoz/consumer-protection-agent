# 两人开发总体框架

## 项目主线

新建案件 → 信息补充 → 事实与法律分析 → 诉求确认 → 多轮协商 → 投诉材料 → 跟进结果 → 用户确认结案。

新反馈可以重新进入协商和分析；页面切换与案件实际处理状态分别维护。打开“投诉准备”页不会自动把案件改成投诉中，生成草稿才记录相应进度。

## 两人分工

| 成员 | 负责目录 | 后续完善的模块 |
| --- | --- | --- |
| A 案件与分析模块 | 对应页面、接口与服务 | 案件创建、信息补充、证据处理、法律检索、案件分析与合理诉求 |
| B 协商与投诉模块 | 对应页面、接口与服务 | 多轮沟通、商家反馈、策略与话术、投诉材料、处理进度和结案 |
| 共同确认 | docs | 案件字段、状态含义、接口返回、错误格式、模拟数据与真实数据边界 |

## 六个业务模块

1. 案件管理：创建、修改事实、阶段、时间线、最终处理结果。
2. 信息与证据：附件上传、OCR、文档提取，标记用户描述、提取结果与 AI 推断。
3. 法律检索：官方来源、法律现行版本、适用条件、核验状态。
4. 诉求决策：诉求分类、金额计算规则、策略建议、用户确认。
5. 沟通协商：保存完整上下文、分析商家回复、重新决策、话术调整。
6. 投诉跟踪：证据缺口、投诉草稿、渠道选择、辅助填表、后续结果。

骨架只展开到以上模块。真实工作流可以在 `backend/app/agents/` 下逐步增加节点，避免过早拆成很多服务。

每人负责业务模块的完整链路，不按前后端分人。公共布局、样式和案件字段先共同约定，再指定维护人。后端接口目前集中在 `main.py`，细化时按业务模块拆分路由，以减少同文件冲突。

## 前端共用规则

- `styles/tokens.css` 是配色和基础风格入口：主色 #315EFB、背景 #F5F7FB、正文 #17243B、白色卡片。
- `styles/global.css` 统一按钮、输入框、卡片、聊天气泡、状态、时间线和响应式布局。
- `styles/layouts.css` 对照设想图定义案件列表、新建对话页、三栏工作台；案件内部不展示全局侧栏。
- 协商建议组件 `NegotiationAdvice.vue` 位于右侧进度栏内部，中间只保留沟通记录和输入区。
- 案件工作台复用左右信息与进度栏，中间按路由替换业务组件，两侧可折叠。
- 新模块优先复用 `.panel`、`.btn`、`.field`、`StatusBadge`、`AppIcon`，不要单独建立一套配色和间距。
- 页面只经 `api/index.js` 访问数据，业务组件不直接写请求地址。
- 前端本地模式只供演示。切到 API 模式后，以后端数据为准。

## 建议开发顺序

1. 先确认本骨架页面结构、视觉风格和接口字段。
2. 接入真实数据库，补充案件信息编辑与基本权限。
3. 优先打磨法律判断、合理诉求和根据商家反馈动态调整策略。
4. 增加 OCR、文档解析和流式响应。
5. 最后研究投诉平台辅助填表和跨平台进度获取。

第一批真实测试建议集中在网购质量与退款纠纷。健身房示例用于对照现有视觉材料，不表示已完成所有预付消费规则。
