# 前后端接口约定

基础路径 `/api`，除文件上传外请求使用 JSON。当前按单用户、本地开发设计。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | /health | 服务状态、当前 Agent 模式 |
| POST | /extract | 从描述中按规则抽取案件字段（不接模型） |
| GET | /cases | 案件列表 |
| POST | /cases | 创建案件 |
| PUT | /cases/{id} | 更新案件基本信息（仅传需要修改的字段） |
| GET | /cases/{id} | 获取完整案件 |
| DELETE | /cases/{id} | 删除整个案件及其已上传文件 |
| POST | /cases/{id}/analysis | 生成演示分析并保存 |
| POST | /cases/{id}/messages | 记录商家回复，返回含演示建议的案件 |
| POST | /cases/{id}/complaint | 生成投诉草稿并保存 |
| POST | /cases/{id}/materials | 上传材料，multipart 的字段名为 files |
| GET | /cases/{id}/materials/{materialId}/download | 下载已上传材料文件 |
| DELETE | /cases/{id}/materials/{materialId} | 删除材料记录与磁盘文件 |
| PATCH | /cases/{id}/materials/{materialId} | 更正材料类型 `kind` |
| POST | /cases/{id}/progress | 添加跟进记录并可更新状态 |

创建案件输入：`title`、`summary`（必填）、`merchant`、`amount`（元）、`goal`、`tradeTime`（交易时间）、`platform`（交易平台）、`product`（商品/服务名称）、`payee`（实际收款方）、`creditCode`（统一社会信用代码）。除 `summary` 外均选填；金额使用非负值；后续金额计算建议改用后端 Decimal 并约定精度。`title` 留空时由后端按「诉求 · 商品」拼接（如 `退货退款 · 护眼台灯`），两者都为空则取描述前 24 字；前端 mock 模式规则相同。

字段抽取：`POST /extract` 请求 `{ "text": "描述原文" }`，长度 1–10000，纯空白返回 422。返回：

```text
fields: { merchant?, amount?, product?, goal?, platform?, tradeTime?, creditCode? }
evidence: [{ field, value, snippet, start, end }]
missing: [{ field, label }]
```

`evidence` 给出每个值在原文中的位置，满足 `text[start:end] == snippet`；只做词表与正则匹配，不做推断，抽不到就进 `missing`（限商家名称、交易金额、商品/服务、交易时间四项）。`goal` 只取最早命中的诉求，多诉求合并由后续诉求确认环节处理。mock 模式由前端 `domain/extract.js` 走同一套规则，不经过接口。

`PUT /cases/{id}` 接收上述字段的子集，未传字段保持不变；另可传 `complaintAttachments`（材料 ID 数组）和 `goalPlan`（诉求计划对象）；`summary` 若传不可为空；已结案（`resolved`）案件不可编辑。

沟通输入：`{ "content": "商家回复原文" }`。

跟进输入：`{ "note": "新的处理反馈", "stage": "following", "confirmed": false, "channel": "market_12315", "caseNo": "12315-2026-0001", "acceptStatus": "pending", "deadline": "2026-11-20", "resolution": { "resolvedWay": "negotiation", "actualAmount": 399, "expectedMet": "yes", "summary": "全额退款到账", "closedAt": "..." } }`。`stage` 可为 null，表示保持当前状态；`channel`、`caseNo`、`acceptStatus`、`deadline` 均选填，空串按 null 处理。改为 `resolved` 时，必须提供 `confirmed: true` 表示用户确认诉求实际履行；`resolution` 为结案总结，仅在确认结案时提交。

结案总结 `resolution`：`resolvedWay` 解决方式（协商或各渠道 key）、`actualAmount` 实际退款/赔偿金额、`expectedMet` 是否达预期（`yes`/`partial`/`no`）、`summary` 结案备注、`closedAt` 结案时间。经历步骤与采取渠道由跟进记录和沟通记录汇总，不单独手填。

渠道 `channel`：`platform` 交易平台售后、`market_12315` 12315 平台/市场监管部门、`hotline_12345` 12345 热线、`consumer_assoc` 消协调解、`industry` 行业主管部门、`justice` 仲裁/法院。渠道的受理范围与所需材料见后端 `services/rules.py` 的 `CHANNELS`，前端 `domain/case.js` 同步一份。

受理状态 `acceptStatus`：`pending` 待受理、`accepted` 已受理、`supplement` 需补充材料、`rejected` 未受理、`contacted` 商家已联系、`resolved` 已履行。

除列表与健康检查外，成功操作统一返回完整案件：

```text
id, title, summary, merchant, amount, goal, stage,
createdAt, updatedAt,
analysis: null | { summary, category, missing[], rights, legal, strategy, script },
messages: [{ id, role, content, createdAt }],
materials: [{ id, name, size, status, storageName?, kind, source, uploadedAt }],
complaint: string,
complaintAttachments: [materialId],
goalPlan: null | { basic, further, negotiable, targetAmount, basis, evidence, confirmed },
resolution: null | { resolvedWay, actualAmount, expectedMet, summary, closedAt },
followups: [{ id, note, stage, confirmed, channel, caseNo, acceptStatus, deadline, createdAt }],
timeline: [{ id, text, createdAt }]
```

`goalPlan` 为诉求结构化计划：`basic` 基础诉求、`further` 进一步诉求、`negotiable` 协商诉求、`targetAmount` 目标金额、`basis` 金额计算依据、`evidence` 证据支持情况（后续分析模块填写）、`confirmed` 用户是否确认。金额合理性与法律依据判断由后续 Agent 模块补充，前端不替用户决定接受多少补偿。`complaintAttachments` 是投诉草稿纳入的材料 ID 列表。

法律结构：`{ name, explanation, source, verified }`。当前 `verified` 恒为 false，禁止将模拟结果展示为已核验法律。后续可扩展法律版本、生效时间和适用条件等字段。

消息角色：`merchant` 是用户录入的商家原文，`assistant` 是系统输出。后续可扩展 `user`、`system`。

阶段：`collecting` 待完善、`analyzing` 分析中、`negotiating` 协商中、`complaining` 投诉中、`following` 待履行、`resolved` 已解决。`complaining` 只表示正在准备或处理投诉，不表示已向真实平台提交。

材料状态：`demo` 示例记录、`metadata` 仅文件元信息、`uploaded` 文件已存储但未解析。

删除案件：`DELETE /cases/{id}` 会一并清理该案件已上传的磁盘文件，返回 `{ "ok": true, "id": "..." }`；案件不存在返回 404。前端入口在案件列表，删除前需用户确认。

材料类型 `kind`：`order` 订单/付款凭证、`contract` 合同/宣传页、`photo` 问题照片/视频、`chat` 沟通记录、`other` 其他材料；上传时按后缀初判，后续可由用户或 Agent 更正。
材料来源 `source`：`user` 用户上传、`extracted` 文件提取、`inferred` AI 推断。
材料下载走 `/materials/{materialId}/download`；示例材料（无 `storageName`）不可下载。删除材料会同步移除磁盘文件。`PATCH /materials/{materialId}` 仅接收 `{ "kind": "chat" }`，用于人工或后续 Agent 更正类型。

跟进记录 `followups` 为结构化列表；`timeline` 仍保留纯文本事件流，提交跟进时会在文本后追加渠道与编号。

错误：业务错误使用 HTTP 400/404/409/413，返回 `{ "detail": "错误说明" }`；字段校验失败为 422。

真实 AI、SSE 事件和外部提交接口尚未实现，接入时先共同确定事件结构与用户确认节点。
