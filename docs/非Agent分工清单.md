# 非 Agent 部分开发清单（本方负责范围）

> 前提：Agent 智能推理部分由另一人负责。本文档只列本方需要开发的内容：页面交互、后端确定性业务、数据模型、静态规则与配置、材料管理、接口契约与工程测试。
> 边界需两人共同确认：标「约定」的条目，必须先和 Agent 负责人对齐入参/出参结构，再各自实现。

## 一、先划边界：哪些归 Agent（对方），哪些归本方

### 归 Agent / 对方负责

- 调用大模型的客户端、密钥与模型选型封装。
- 提示词模板、模型编排工作流（LangGraph 或函数链）、多轮上下文调度。
- 智能输出：事实抽取与补全建议、纠纷分类结论、法律依据分析、诉求与金额建议、谈判策略、话术生成、商家回复语义分析、推诿识别、渠道推荐理由、相似案例参考。
- 模型流式输出、RAG 检索调用、OCR/多模态识别的模型侧逻辑。

### 归本方负责（本清单范围）

- 前端全部页面、组件、表单、展示与交互。
- 后端数据模型、CRUD、文件存储、状态流转、确定性组装。
- 静态规则与配置数据（枚举、渠道表、材料清单、模板占位），不含模型推理。
- 前后端接口契约、mock 桩、联调与测试。
- 把前端输入收敛成 Agent 入参，把 Agent 出参落库并渲染到页面。

### 灰色地带（必须先约定，避免重复或漏做）

| 事项 | 建议归属 | 说明 |
| --- | --- | --- |
| 本地法条/规则条目数据 | 条目结构与展示本方，条文内容核验对方或共同提供 | 先定字段：名称、条款、通俗解释、适用条件、来源、生效/废止、核验状态 |
| RAG 检索服务 | 检索接口与数据落库可本方，召回逻辑可双方协商 | 先定检索入参（纠纷类型、关键词）和返回结构 |
| 状态机流转 | 触发条件与落库本方，策略建议 Agent 给 | 例如是否转投诉：规则条件本方判断，理由和话术 Agent 给 |
| 证据缺口清单 | 清单规则条目本方，是否缺证据的语义判断 Agent 可辅助 | 先按纠纷类型做确定性清单核对 |
| 投诉材料组装 | 结构化拼装本方，事实与法律表述由 Agent 生成 | 本方负责字段填充、排版、复制导出 |

## 二、当前骨架已完成、可继续沿用

- 前端：案件列表/搜索/筛选、新建表单、三栏工作台与折叠、四个页签、协商记录与话术复制、投诉草稿展示、跟进时间线、结案确认勾选、个人昵称电话、路由与 Pinia、mock/API 双模式。
- 后端：案件 CRUD、分析/消息/投诉/材料/进度接口、上传校验、SQLite JSON 存储、入参校验、接口主流程测试。
- 这些已有链路继续对接新字段即可，不需要推倒重写。

## 三、本方待开发：前端

### 1. 案件信息与表单

- 扩展新建/编辑表单字段：交易时间、交易平台、商品或服务名称、实际收款方、商家名称、统一社会信用代码、交易金额、当前诉求、已沟通过程。
- 表单校验：必填、长度、金额非负与精度、手机号/身份证号格式校验（提示性，不做实名核验）。
- 信息补充页：按缺口清单逐项表单/问答式补充（确定性表单，不是 AI 追问）；缺口项标记"待补充"。
- 案件详情左侧栏：渲染全部结构化事实字段，空值展示占位。

### 2. 证据材料管理界面

- 材料列表：文件名、大小、类型、上传时间、状态（示例/仅元信息/已上传待解析/已解析）。
- 上传交互：多选、类型与大小校验、上传中状态、失败提示。
- 材料操作：预览（图片直显、文本下载）、下载、删除（二次确认）。
- 证据缺口提示区：按材料清单展示已具备/缺失条目（数据来自后端规则核对）。
- 来源标记展示：用户上传 / 文件提取 / AI 推断（字段由后端落库，本方只展示）。

### 3. 工作台与进度

- 三栏布局、左右折叠、步骤进度条、上一步/下一步对接新状态枚举。
- 阶段状态徽章与状态说明文案统一管理。
- 确认节点 UI：诉求确认、话术发送前、接受和解、提交投诉、结案，均为独立确认按钮/勾选，未确认不进入下一步。

### 4. 协商页

- 聊天记录时间线展示（用户录入的商家原文、系统建议、用户消息分角色）。
- 商家回复录入框与校验；话术展示框、复制、语气/风格选择 UI（选项数据来自配置，不生成内容）。
- 预留流式消息渲染位（对方接 SSE 后直接对接）。
- 法律依据/建议卡片折叠展示，结构化字段分区呈现。

### 5. 投诉准备与渠道选择

- 问答式分步填表：投诉对象、交易情况、事实经过、商家问题、已协商过程、具体诉求、证据附件清单；已有信息预填，用户可修改。
- 渠道选择卡片：渠道名称、受理条件、适用范围、所需材料、推荐理由展示（数据来自后端规则表/Agent 建议）。
- 投诉材料预览：结构化分区展示、复制、导出文本；附件清单核对状态。
- 明确提示：本方不向任何外部平台提交，提交由用户在平台完成或后续迭代。

### 6. 跟进与结案

- 结构化跟进表单：投诉渠道、投诉编号、受理状态、是否需补材料、新反馈、处理期限。
- 时间线按节点展示：提交时间、受理、补材料、商家联系、新方案、到账等。
- 结案总结表单：最终解决方式、实际退款/赔偿金额、经历步骤、采用渠道、是否达到预期。
- 结案确认勾选逻辑沿用现有规则：未确认实际履行不能置为已解决。

### 7. 个人中心

- 维护姓名、手机号、身份证号等身份信息；本地存储，列表与表单中脱敏展示（手机号、身份证号掩码）。
- 资料只用于后续投诉填写，不自动对外提交，页面有说明文案。

### 8. 公共组件与样式

- 复用现有 `.panel`、`.btn`、`.field`、`StatusBadge`、`AppIcon`；补齐确认弹窗、空态、错误提示、表单校验提示、加载态。
- 响应式布局核对；配色沿用 `tokens.css`，不另起一套风格。

## 四、本方待开发：后端确定性业务

### 1. 数据模型与表结构

- 当前单表 JSON 聚合，按需拆分：案件、消息、材料、诉求项、跟进记录、渠道/投诉记录、个人资料。
- 字段扩展：交易时间、平台、商品/服务、收款方、经营主体、信用代码、材料条目、诉求项、跟进节点。
- 枚举集中定义：案件阶段、纠纷类型、诉求类型、材料状态、渠道类型、消息角色。
- 金额改 Decimal，约定精度与四舍五入口径。
- 保留 SQLite 默认可跑，MySQL 切换配置沿用现有 `DATABASE_URL`。

### 2. CRUD 与校验接口

- 案件：创建、详情、列表（按阶段/关键词/更新时间筛选排序）、事实字段编辑。
- 消息：记录商家原文/用户消息/系统建议，绑定案件与时间。
- 材料：上传、列表、下载、删除；类型/大小/空文件校验沿用现有逻辑；存储名独立生成，不使用用户路径。
- 跟进：添加反馈、更新阶段、记录渠道与编号、结案确认校验。
- 资料：保存与读取个人身份信息。
- 入参 schema 校验、统一错误格式（400/404/409/413/422）、分页与返回结构约定。

### 3. 静态规则与配置数据（不含模型推理）

- 纠纷类型枚举与名称表。
- 诉求类型枚举、三层归属（基础/进一步/协商）的字段定义。
- 投诉渠道映射表：渠道、受理条件、适用范围、所需材料、注意事项、渠道分类（行政投诉/举报/平台投诉/司法救济）。
- 证据缺口清单：按纠纷类型列出必备/可选材料。
- 状态机定义：阶段流转条件、哪些操作触发哪个阶段、结案前置条件。
- 话术模板占位与语气/风格选项枚举（文本骨架由本方落库，具体措辞对方 Agent 生成）。

### 4. 确定性组装与流转逻辑

- 投诉材料拼装：按结构化字段生成草稿文本/结构，事实只取已录入内容，不补不存在的事实。
- 时间线记录：关键操作自动写入节点与时间。
- 阶段流转规则：根据材料、消息、投诉草稿、跟进反馈更新阶段；页面切换不改状态。
- 证据齐全度计算：基于清单规则统计已备/缺失条目。
- 结案校验：必须 `confirmed=true` 且记录实际履行结果；口头同意/提交成功不算解决。

### 5. 文件存储与安全预留

- 上传目录管理、下载接口与访问控制；材料删除同步删文件。
- 敏感字段标记与脱敏方案预留；访问控制、数据保留期位置预留（认证后续迭代）。
- `.env` 管理：数据库、CORS、上传目录、大小限制；密钥不入库。

### 6. Agent 接口桩与联调契约

- 在业务服务中预留 Agent 调用点：定义好入参（案件事实、历史消息、材料元信息、当前阶段）和出参结构（分析、诉求、话术、建议、确定程度、来源标记）。
- 未接入前用本地 mock/规则桩返回占位结构，保证前端和后端流程可独立跑通。
- 与对方共同确认：字段名、类型、可空性、错误降级结构、流式事件格式。

### 7. 测试与工程

- 单元/接口测试：CRUD、字段校验、阶段流转、结案校验、上传下载删除、材料清单核对、渠道表完整性。
- mock 引擎与后端规则输出对齐，双模式行为一致。
- 依赖整理、`.env.example`、README 运行步骤、接口文档更新。

## 五、本方不做、明确留给对方

- 模型客户端、密钥管理、提示词、工作流编排与多轮调度。
- 任何语义判断与自然语言生成：抽取、分类、法律解释、诉求建议、话术、回复分析、策略推荐、案例检索。
- RAG 召回、OCR/多模态识别、流式模型输出的生成侧。
- 外部投诉平台自动化填表与进度自动获取（双方后续共同评估）。

## 六、建议开发顺序

1. 与对方对齐接口契约：案件事实、分析、诉求、话术、跟进记录的入参/出参结构和确认节点。
2. 后端数据模型 + 枚举 + CRUD + 校验接口，先用 mock 桩跑通。
3. 静态规则表：渠道映射、证据清单、状态机、诉求类型、模板占位。
4. 前端表单与页面：信息补充、材料管理、投诉分步填表、渠道选择、跟进结构化、结案总结、个人资料。
5. 文件存储、下载删除、脱敏预留与错误处理。
6. 测试补齐与文档更新；最后留出对接位，等对方 Agent 实现替换桩。
