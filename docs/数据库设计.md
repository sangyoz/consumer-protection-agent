# MySQL 模块拆表

业务数据实际写入各模块表，`cases` 不再有保存整个案件的 `payload` 字段。API 和 Agent 仍使用原来的案件对象，转换集中在 `backend/app/services/case_repository.py`，前端不需要修改。

| 表 | 内容 / 主要列 |
| --- | --- |
| `users` | 用户：`id`、`username`、`password_hash`、`created_at` |
| `user_sessions` | 登录会话：`token_hash`、`user_id`、`expires_at` |
| `cases` | 案件基本信息：`id`、`user_id`、`title`、`summary`、`merchant`、`amount`、`goal`、`platform`、`product`、`payee`、`credit_code`、`trade_time`、`stage`、`created_at`、`updated_at` |
| `messages` | 对话：`case_id`、`position`、`id`、`role`、`content`、`created_at` |
| `materials` | 材料：`case_id`、`position`、`id`、`name`、`size`、`storage_name`、`kind`、`status`、`source`、`uploaded_at` |
| `evidence_items` | 证据清单：`case_id`、`position`、`key`、`label`、`status`、`note`、`content_verified` |
| `case_steps` | 处理步骤：`case_id`、`position`、`id`、`type`、`title`、`status`、`reason`、`completion_condition`、`note`、`feedback_at` |
| `progress_records` | 处理跟进：`case_id`、`position`、`id`、`step_id`、`note`、`stage`、`status`、`channel`、`case_no`、`accept_status`、`deadline`、`confirmed`、`created_at` |
| `case_events` | 时间线：`case_id`、`position`、`id`、`text`、`created_at` |
| `case_plans` | 案件流程元信息：`case_id`、`version`、`locked`、`engine`、`reason`、`current_step_id`、`updated_at`；其他维权建议保存在扩展 JSON |
| `case_analyses` | 案件分析与文书：`case_id`、`analysis`、`agent_state`、`complaint`、`complaint_attachments`、`goal_plan`、`resolution` |

`cases.user_id` 关联 `users.id`。各子表通过 `case_id` 外键关联案件；案件删除时，ORM 与数据库的级联规则会清理关联记录。子表以 `(case_id, position)` 作为复合主键，`position` 从 0 开始，保留原数组顺序；`id` 保留原有消息、文件、步骤标识，不受数据库行位置影响。流程首次生成后固定的业务规则保持不变。

常用数据使用独立字段；动态的模型输出、引文、诉求计算、结案详情、替代方案与未来扩展字段使用 JSON。`field_names` 保留原接口中缺省与空值的区别，`extra_data` 仅保存未定义为固定列的扩展信息，不再把对话、材料等业务列表整体塞入 JSON。

## 迁移

停止应用写入后，启动脚本启动后端时会自动检查并执行迁移：

1. 将旧数据（包含账号和原始案件 JSON）备份到 `.run/backups/relational-before-*.json`，不在日志打印用户内容。
2. 建立缺失的字段、子表、索引与外键，保留原案件 ID、账号归属、文件存储名。
3. 在事务中将旧 JSON 拆入各表。
4. 使用新数据库会话重新读取，逐案比对完整对象，包含步骤顺序、对话、材料和扩展信息。
5. 全部一致后移除旧 `payload` 列；后续启动不会再执行旧数据导入。

MySQL 的建表和改表会隐式提交，因此这里不声称整个迁移可用一个事务回滚；校验失败会保留旧列与备份，可在停止应用后修复并重试。备份包含个人数据与密码哈希，仅留在 Git 忽略目录，不应上传。上传文件本身仍位于 `backend/uploads/`；法律检索库仍独立使用 `backend/legal.sqlite3`。

## Workbench 查看

刷新左侧 `SCHEMAS` 并展开 `youli → Tables`。

```sql
SELECT id, title, merchant, amount, stage, user_id FROM youli.cases;
SELECT case_id, position, role, content FROM youli.messages ORDER BY case_id, position;
SELECT case_id, position, title, status, note FROM youli.case_steps ORDER BY case_id, position;
SELECT case_id, name, storage_name, kind FROM youli.materials;
```

只读查看工具继续可用：在 `backend` 执行 `.\.venv\Scripts\python.exe tools\dump_db.py` 查看表数量，追加 `cases` 或 `cases --full` 查看组装后的案件。`--db youli.db` 专用于查看旧 SQLite 备份。
