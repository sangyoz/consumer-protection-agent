# 待办流程与先行开发清单

> 对照《基本要求和流程.docx》十步流程、两张手绘设想图，以及当前仓库实际代码盘点。
> 结论基于仓库现状：前端 Vue 骨架 + 后端 FastAPI 骨架，Agent 为关键词/模板模拟，未接真实模型、法律检索、OCR 与外部平台。

## 一、当前骨架已经完成的部分

### 前端（frontend/src）

- 案件中心：案件卡片列表、搜索、全部/处理中/已解决筛选、进度条与状态徽章。
- 新建案件：左侧历史案件栏 + 右侧自然语言输入框，附三个示例问题；可填标题、商家、金额、诉求。
- 三栏工作台：左侧案件基本信息 + 证据材料（可折叠），中间对话/业务区，右侧进度条 + 建议 + 上一步/下一步（可折叠）。
- 四个业务页签：案件分析、沟通协商、投诉准备、其他方案。
- 沟通协商：商家回复录入、聊天记录展示、话术语气三选（理性坚定/温和协商/正式严肃）、复制话术。
- 投诉准备：证据有无勾选、纯文本投诉草稿生成与复制。
- 处理跟进：时间线查看、反馈录入、状态更新、结案必须勾选"确认实际履行"。
- 个人中心：昵称、手机号（仅存浏览器 localStorage）。
- 工程：路由、Pinia store、mock/API 双模式封装、公共样式与设计变量。

### 后端（backend/app）

- FastAPI 接口：`/health`、案件列表/创建/详情、分析、消息、投诉草稿、材料上传、进度更新。
- SQLite JSON 聚合存储；上传文件落 `backend/uploads/`，做了类型、大小、空文件、整批校验。
- 模拟 Agent：关键词二分类（预付式 / 商品服务）、模板话术、关键词三分类回复建议、投诉草稿拼接。
- Pydantic 入参校验；结案确认校验；内存数据库 + 临时目录的接口测试。
- LangGraph 工作流、真实 LLM、法律检索、OCR、流式输出均为占位。

- 图 2（协商双栏 / 投诉 / 其他 / 个人主页）：协商左记录右建议、投诉草稿、其他方案占位已落地；个人主页只做了昵称电话，身份证号等身份信息未做；"咨询律师"入口、联网找相似案例未做。

## 二、对照十步流程的未做清单

### 第一步：创建维权任务、多模态信息理解

现状：只有标题、描述、商家、金额、诉求五个手填字段；附件只存文件或仅记录文件名，不解析。

待办：

1. 结构化事实字段：交易时间、交易平台、商品/服务名称、实际收款方、是否已联系商家、商家回应、是否已退款。
2. 信息来源标记：区分"用户主动描述 / 文件提取 / AI 推断"；不确定信息不得当作事实。
3. 材料解析链路：PDF / DOCX / TXT 文本提取，图片 OCR，聊天记录、订单、合同、付款凭证要素抽取；录音、视频留扩展位。
4. 材料管理：列表预览、下载、删除、按类型归类；当前无下载与删除接口。
5. 信息缺口收集：关键信息不足时，以问答形式逐步追问，而不是一次性大表单。

### 第二步：纠纷分析与法律依据

现状：纠纷类型仅关键词二分类；法律卡片为占位，`verified` 恒为 false，无任何已核验结论。

待办：

1. 纠纷分类规则覆盖文档列出的类型：质量问题、虚假宣传、拒绝退款、售后纠纷、预付式消费、价格收费争议、食品安全、服务未按约定履行等。
2. 本地法律知识库结构：法律名称、条款内容、生效时间、适用范围、官方来源、现行有效/废止标记。
3. 法律建议四段式展示：法律规定原文、通俗解释、对本案的意义、适用条件与当前证据是否具备。
4. 区分三类权利：法定权利、需满足条件才能主张的权利、协商可争取的额外补偿；惩罚性赔偿须校验欺诈等法定条件，不得直接承诺退一赔三。
5. 结论确定程度标记；大额、复杂合同、重大后果案件提示寻求专业法律帮助。

### 第三步：诉求与谈判目标

现状：诉求只有一句 `goal` 文本；无金额估算、无诉求分层、无用户确认节点。

待办：

1. 诉求结构化：诉求类型、目标金额、计算依据、法律依据、证据支持情况、是否协商诉求、用户是否确认。
2. 诉求三层：基础诉求（法定/约定）、进一步诉求（有事实和依据时的额外赔偿）、协商诉求（可争取的服务/优惠/适当补偿）。
3. 金额计算规则化：退货退款、预付款余额、实际损失、惩罚性赔偿条件校验，用明确公式或规则，不交由模型自由估算；金额用 Decimal 并约定精度。
4. 谈判目标：优先争取项、依据强弱、可让步空间、替代方案、不可让步底线；不得替用户决定接受多少补偿或放弃权利。

### 第四步：沟通策略与第一轮话术

现状：语气切换只是三段固定前缀；策略为一句模板；无"先讲依据再给话术"的结构。

待办：

1. 策略按场景生成：沟通态度、先陈述事实还是先提要求、是否引用法律、是否要求对方先给方案、是否保留投诉权利。
2. 话术风格库：理性协商型、明确诉求型、法律依据型、正式交涉型，按商家态度和场景选用。
3. 话术结构：本次法律依据 → 案件分析 → 为什么建议这种方式 → 可直接发送的话术。
4. 话术可调：语气、长度、表达方式；法律解释折叠展示，不堆砌条文。

### 第五步：商家回复分析与动态调整

现状：回复按关键词归入等待/拒绝/其他三类；无推诿方式识别、无案例参考、无重新决策。

待办：

1. 商家回复分类：接受诉求、部分退款、以公司规定拒绝、要求等待、否认问题、归咎用户、不再回复等。
2. 常见推诿识别：拖延、模糊责任、归咎消费者、以内部规定代替法律、低价补偿、反复要求重复说明。
3. 每轮分析结合案件事实、诉求、完整历史记录重新判断：是否回应核心诉求、理由是否有据、方案是否合理、是否需补证据、继续协商还是转投诉。
4. 相似案例参考分层：官方法规/典型案例、裁判文书与调解案例、社交平台真实经历；社交内容只作经验参考并做可靠性标记。
5. 输出须经用户确认后再发送，不替用户承诺、和解或放弃权利。

### 第六步：协商结果判断与渠道选择

现状：协商成功/失败无结构化判断；"其他方案"页为空壳，无渠道推荐。

待办：

1. 协商成功确认项：具体金额、处理方式、完成时间、遗留问题；口头同意不算解决，实际履行到账才结案。
2. 渠道映射表：交易平台内部投诉、12315/市场监管、12345、消协调解、行业监管部门、仲裁/法院、涉嫌诈骗报公安；按纠纷类型、主体、平台、证据情况推荐，不机械全推。
3. 渠道资料：受理条件、适用范围、办理要求；区分行政投诉、举报、商业平台投诉、司法救济；第三方平台结果不等同政府正式处理。

### 第七步：证据整理与投诉材料

现状：投诉草稿为纯文本拼接；证据缺口只做了三个有无勾选；无结构化证据清单。

待办：

1. 证据条目化：订单/付款凭证、问题照片视频、合同与宣传页、沟通记录、拒绝或不合理方案记录，逐条关联事实。
2. 证据缺口识别：按纠纷类型清单核对缺什么（如健身房停业需补门店停业照片、会员卡记录、剩余课程、付款凭证、联系记录），并提醒补充。
3. 投诉材料结构化：投诉对象、交易情况、经过、商家问题、已协商过程、法律依据、具体诉求、证据附件清单。
4. 事实约束：材料只能基于用户提供的事实和可验证证据，不得自行补不存在的事实。

### 第八步：辅助填写投诉平台

现状：仅生成文本草稿，不填表、不提交。

待办（初期定位：辅助填写 + 用户确认提交，不追求无人值守）：

1. 表单字段级整理：投诉对象、经营主体名称、统一社会信用代码（可获得且核实情况下）、事实经过、诉求、附件清单。
2. 问答式填表：先不做自动填表，分步问答收集信息并预填，用户核对修改。
3. 用户确认节点：核对对象与个人信息、检查事实诉求、确认附件、完成身份验证、最终确认提交。
4. 预留 Browser Use / 浏览器自动化研究位；注意平台规则、验证码、身份认证须用户亲自完成；提交、撤回、和解、签协议必须用户明确确认。

### 第九步：跟进投诉进度

现状：只有自由文本时间线；无渠道、编号、受理状态等结构化跟进字段。

待办：

1. 跟进记录结构化：投诉提交时间、渠道、投诉编号、当前状态、相关反馈、每次补材料与商家反馈。
2. 状态判断：是否受理、是否需补材料、商家是否联系、是否提出新方案、是否继续协商、是否转其他渠道。
3. 节点提醒：重要时间节点记录与提醒；新信息进入后重新评估法律依据和诉求。
4. 进度获取：手动更新为主；接口或自动化获取进展作为后续迭代，不把提交成功等同于维权成功。

### 第十步：确认结果、结束任务

现状：结案只有一个确认勾选 + 文本时间线；无结果总结。

待办：

1. 结案总结：最终解决方式、实际退款/赔偿金额、经历步骤、采用的沟通与投诉方式、是否达到预期。
2. 案例沉淀：获用户授权并脱敏后，用于后续产品优化与匿名案例分析。

## 三、横向缺口（不对应单一步骤）

1. 数据模型：当前单表 JSON 聚合，后续宜拆案件、消息、材料、诉求、时间线、渠道/投诉记录等结构。
2. 账户与权限：无登录认证、无案件权限隔离；当前定位本机单用户骨架，需预留方案。
3. 隐私安全：订单、合同、聊天记录、身份证明等敏感信息缺加密、访问控制、脱敏与保留期管理。
4. 真实 AI 接入：LLM 客户端、SSE 流式输出、事件结构、用户确认节点约定均未实现。
5. 法律知识与检索：本地知识库、检索核验、现行有效性校验未做。
6. 金额与字段规范：金额改 Decimal 精度；补充经营主体、信用代码、交易时间、平台等字段。
7. 后端服务拆分：当前接口集中在 `main.py`；按案件、分析、诉求、协商、证据、投诉、渠道、跟进、个人资料拆路由与服务。
8. 清理残留：`backend/app/**/__pycache__` 中残留 amounts、channels、evidence、followup、form_builder、llm、other_plan、profile、references、retrieval、solutions 等字节码，但对应 `.py` 源码不在仓库；可作为服务拆分命名参考，建议清理缓存后按规划重建。
9. 测试覆盖：现有接口主流程测试；规则分类、金额计算、证据缺口、渠道映射、状态流转需补单元测试。

## 四、先不接 LLM API、外部 RAG / 检索，还能先开发什么

原则：这一阶段用"本地静态数据 + 规则引擎 + 前端交互 + 结构化接口"把流程跑通，所有智能判断先用确定性规则或模板占位，代码结构预留后续替换为模型的位置。

### P0：先把数据模型和接口结构定下来（不依赖任何外部能力）

1. 扩展案件与相关实体字段，前后端 schema 对齐：交易时间、平台、商品/服务、收款方、经营主体、信用代码、证据条目、诉求项、渠道记录、跟进节点。
2. 明确各对象结构：分析结果（分类、缺口、权利、法律依据、策略、话术）、诉求项、材料条目、渠道推荐、投诉表单、跟进记录；与 `docs/接口约定.md` 同步更新。
3. 金额改 Decimal，约定精度与计算口径；枚举值（阶段、纠纷类型、诉求类型、材料状态、渠道类型）集中定义。
4. 后端按模块拆路由/服务骨架，每个服务先返回规则或空结构，预留 `agent.workflow` 调用点。

### P0：本地静态知识库与规则表（纯配置，不联网、不调模型）

1. 纠纷分类规则表：关键词/条件 → 纠纷类型。
2. 法律条款样本库（本地内置）：条款要点、通俗解释、适用条件、来源、生效/废止标记；样本可标注为"本地示例，非联网核验"。
3. 诉求类型与三层规则、金额计算规则：退货退款、预付款余额、实际损失、惩罚性赔偿条件校验等公式化规则。
4. 投诉渠道映射表：渠道、受理条件、适用范围、所需材料、注意事项；按纠纷类型给出推荐顺序。
5. 商家回复规则分类表：拖延、拒绝、部分退款、否认问题、归咎用户、沉默等关键词与判定条件。
6. 证据缺口清单：按纠纷类型列出必备材料与可选材料。
7. 话术模板库：四种风格 + 语气/长度组合，模板拼装，不调模型。

### P1：前端流程补全（确定性 mock 即可闭环）

1. 信息补充问答流程：按缺口清单逐项表单/对话补充，更新结构化事实。
2. 诉求确认页：三层诉求卡片、金额及计算依据展示、证据支持情况、用户确认勾选。
3. 投诉问答式填表：分步表单（对象、事实经过、诉求、证据清单、渠道选择），整合已有信息预填，用户核对修改；导出结构化草稿。
4. 渠道选择页：渠道卡片 + 受理条件 + 所需材料，按规则推荐。
5. 证据管理：材料预览/删除、缺口提示、来源标记展示。
6. 跟进页结构化：渠道、编号、受理状态、补充材料、节点提醒；状态机推进。
7. 结案总结页：解决方式、实际金额、步骤、渠道、是否达预期。
8. 个人中心：姓名、手机号、身份证号等身份信息本地存储与脱敏展示。
9. 协商状态机界面：规则分类结果 → 本地策略分支（继续协商 / 补证据 / 转投诉）的确定性提示。

### P1：后端规则服务与编排骨架（本地实现，预留模型替换）

1. 事实整理 → 信息补充 → 分类 → 诉求分析 → 策略建议的节点编排，先用规则实现，输出结构化结果。
2. 各规则服务：分类、诉求与金额、证据缺口、渠道推荐、回复分类、投诉材料组装、跟进状态判断。
3. mock 引擎与后端规则保持一致，保证 mock / API 双模式行为对齐。
4. 补齐错误格式、字段校验、单元测试。

### P2：工程与本地可做的解析

1. 本地文本解析：TXT、DOCX 文本提取先落地；图片 OCR、录音/视频解析留接口位。
2. 材料文件流转：预览、下载、删除接口与静态访问策略。
3. 隐私与脱敏方案设计：敏感字段标记、展示脱敏、数据保留策略；登录认证预留接口。
4. 文档补齐：事件结构、用户确认节点、mock 与真实数据边界。

### 必须等 Agent / 外部能力接入后再做的部分

- 自然语言事实抽取、对话式追问理解（当前用表单 + 规则兜底）。
- 真实法律检索、法条现行有效性核验、案例检索与联网搜索。
- 个性化动态话术生成、商家回复语义理解与心理博弈分析。
- 相似案例的社交平台检索与参考。
- 模型流式输出（SSE）与多模态理解。
- 外部投诉平台自动化填表与进度自动获取。

## 五、建议推进顺序

1. 对齐并固化案件/诉求/证据/渠道/跟进的数据结构与接口约定。
2. 后端拆服务骨架 + 本地规则表（分类、诉求金额、证据缺口、渠道映射、回复分类、话术模板）。
3. 前端按流程补齐信息补充、诉求确认、问答式填表、渠道选择、跟进结构化、结案总结、个人资料。
4. 本地文本解析、材料管理、测试与规则校验闭环。
5. 最后接入 LLM API、法律 RAG / 检索、OCR 多模态、流式输出，以及外部平台辅助填表与自动跟进。
